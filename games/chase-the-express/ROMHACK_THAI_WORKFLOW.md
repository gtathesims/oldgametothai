# คู่มือเริ่มโปรเจกต์แปลเกมเป็นภาษาไทย

> แนวทางหลักสำหรับเกม PS1 และเกมเก่าที่มีข้อความ ฟอนต์ และภาพฝังอยู่ในไฟล์เกม ใช้เป็นคู่มือเริ่มงานกับเกมใหม่ได้ โดยต้องสำรวจรูปแบบไฟล์และระบบแสดงข้อความของเกมนั้นก่อน
>
> เรียบเรียงจากงานแปลเกมที่ทำจริง: สำรวจแผ่น → พิสูจน์ตำแหน่งข้อความ → ทดสอบไทย → ส่งออก CSV → ตรวจคำแปล → นำเข้า → แก้ข้อความบนภาพ → ทดสอบ → สร้างแพตช์ → ลงเว็บ วิดีโอเป็นงานเสริมที่ทำภายหลังได้

## 1. เส้นทางทำงานที่แนะนำ

```text
เก็บต้นฉบับและค่าแฮช
        ↓
สำรวจไฟล์ ข้อความ ฟอนต์ ภาพ และระบบโหลด
        ↓
ผู้เล่นเลือกประโยคที่ไปทดสอบซ้ำได้ง่าย
        ↓
เปลี่ยนเป็นข้อความทดสอบด้วยภาษาเดิม
        ↓
ทำต้นแบบฟอนต์ส่วนประกอบ → ตรวจภาพและงบ RAM → ทดสอบไทยกับประโยคเดิม
        ↓
พิสูจน์ระบบอื่นที่จำเป็น เช่น เมนู เอกสาร ตัวเลข
        ↓
ดึงข้อความที่ค้นพบเป็น CSV พร้อมตำแหน่งและบริบท
        ↓
ผู้แปลแปล → ตรวจภาษา → สร้างฟอนต์ส่วนประกอบจากคำแปลทั้งหมด
        ↓
ตรวจภาพทั้งหมดอัตโนมัติและวัด RAM รวม → นำเข้าเป็นชุด
        ↓
ถ้าข้อความเป็นภาพ: แก้ texture และนำภาพกลับ
        ↓
[ทางเลือกภายหลัง: ดึงวิดีโอ → ฝังซับ → นำกลับ]
        ↓
ทดสอบการแสดงผลและการเล่นทุกระบบที่เปลี่ยน
        ↓
สร้างแพตช์จากต้นฉบับ → ลงกลับและเทียบไฟล์
        ↓
เตรียมเว็บ → ทดสอบจากเว็บจริง → เผยแพร่
```

อย่าให้การแปลทั้งเกมเป็นขั้นแรก ควรพิสูจน์ว่าประโยคตัวอย่างแสดงไทยและเล่นต่อได้ก่อน เพื่อไม่ให้แปลจำนวนมากแล้วพบว่านำกลับไม่ได้

| ขั้น | สิ่งที่ต้องได้ก่อนเดินต่อ |
|---|---|
| สำรวจ | ระบุต้นฉบับ รูปแบบแผ่น ไฟล์ที่น่าสนใจ และข้อสงสัย |
| ทดสอบภาษาเดิม | ประโยคที่เลือกเปลี่ยนจริงในจุดที่ผู้เล่นระบุ |
| ทดสอบไทย | ต้นแบบฟอนต์ส่วนประกอบผ่านการตรวจภาพ/ขอบเขต RAM อ่านได้ และเล่นผ่านเหตุการณ์นั้น |
| ส่งออก CSV | มีรหัสคงที่ บริบท ตำแหน่งต้นทาง และรายงานขอบเขต |
| นำเข้า | ตรวจฟอนต์ครบชุดและงบ RAM ใหม่จากคำแปลจริง โครงสร้างไฟล์ถูกต้อง และมีผลทดสอบในเกม |
| แพตช์ | ใช้กับต้นฉบับที่ระบุแล้วได้ไฟล์ตรงกับรุ่นที่ทดสอบ |
| เว็บ | ดาวน์โหลดครบ สร้าง BIN ถูกต้อง และ CUE อ้างอิงชื่อที่บันทึกจริง |

## 2. แบ่งหน้าที่ให้ทำงานเร็ว

**ผู้ทำเครื่องมือหรือผู้ช่วย AI** สำรวจโครงสร้าง หา encoding และตำแหน่งข้อความ ทำเครื่องมือดึง/นำเข้า ฟอนต์ texture ตรวจไฟล์ และจัดแพตช์

**ผู้แปลและผู้ทดสอบ** เลือกข้อความที่เข้าถึงได้ ส่งภาพและวิธีเดินทางไปจุดนั้น แปล CSV และเล่นทดสอบผล โดยเฉพาะหลังรับไอเทม หลังบทสนทนา และหลังเปลี่ยนฉาก

ให้ผู้เล่นเปิดเกมเองเมื่อพร้อมทดสอบ ผู้ทำเครื่องมือต้องส่งชื่อ CUE ของรุ่นทดสอบ จุดที่จะเห็นการเปลี่ยน และสิ่งที่ต้องลองให้ชัด อย่าเปิดเกมหรือเดินเกมเองหากผู้ใช้กำหนดว่าจะเป็นคนทดสอบ

## 3. เตรียมต้นฉบับและโฟลเดอร์งาน

### 3.1 ระบุตัวเกมให้แน่นอน

- ชื่อเกม แพลตฟอร์ม ภาษา/ภูมิภาค และเลขรุ่นที่ทราบ
- จำนวนแผ่น รูปแบบไฟล์ เช่น BIN/CUE, ISO หรือรูปแบบเฉพาะ
- ไฟล์ทุก track ของแผ่นนั้น ไม่ถือว่าเกมทุกเกมมี BIN เพียงไฟล์เดียว
- โปรแกรมและการตั้งค่าที่ใช้ทดสอบ พร้อมผลว่าเกมต้นฉบับเล่นได้
- SHA-256 และขนาดของไฟล์ต้นฉบับแต่ละไฟล์; CRC32 ใช้ตรวจรวดเร็วเพิ่มเติมได้

ต้นฉบับต้องเก็บไว้แยกและไม่แก้ไข สร้างไฟล์ผลลัพธ์ใหม่ทุกครั้ง หากต้นฉบับคนละภูมิภาคหรือคนละ revision อย่าฝืนใช้ตำแหน่งจากอีกชุด

### 3.2 โครงสร้างตัวอย่าง

```text
project/
  originals/              ต้นฉบับที่ไม่แก้ไข
  romhack/
    analysis/             แผนผังไฟล์ รายงาน และหลักฐานการสำรวจ
    extracted/            ไฟล์ที่ดึงออกมาโดยยังไม่แก้
    translation/          CSV คำแปลและรายงานการเกลา
    textures/             ภาพต้นฉบับ ภาพแก้ และข้อมูล palette
    tools/                เครื่องมือสำหรับเกมนี้
    build/                ผลลัพธ์แยกตามรุ่น
    release/              แพตช์ CUE และคู่มือผู้เล่น
    web/                  หน้าเว็บและรายการแพตช์
  PROJECT_STATUS.md       สถานะล่าสุดสำหรับกลับมาทำงานต่อ
```

ชื่อโฟลเดอร์ปรับได้ แต่ต้องแยกต้นฉบับ ไฟล์แก้ และผลลัพธ์ให้เห็นชัด ห้ามใช้ชื่อไฟล์เหมือนกันจนไม่รู้ว่ากำลังเปิดรุ่นไหน

## 4. สำรวจโครงสร้างเกมก่อนแก้

### 4.1 สำรวจระบบแผ่นและไฟล์

อ่านข้อมูล track และระบบไฟล์ที่เกมใช้ ทำรายการพาธ ขนาด ตำแหน่งบนแผ่น และชนิดไฟล์จริง ตรวจไฟล์โปรแกรมหลัก archive, script, font, texture, เสียง และวิดีโอ

เกม PS1 อาจมีข้อมูลหลายชนิดใน BIN เดียว รวมถึงข้อมูลที่ไม่ได้อ่านผ่านรายการไฟล์ปกติ ชื่อหรือนามสกุลไฟล์เป็นเพียงเบาะแส ต้องตรวจ header และเนื้อหาจริงด้วย

ถ้ามี archive ให้ดึงไฟล์และตรวจว่านำกลับโดยไม่เปลี่ยนเนื้อหาได้ก่อน บันทึก offset, ขนาด, alignment, compression, checksum และความสัมพันธ์ระหว่างรายการ หากยังไม่รู้รูปแบบ ให้เขียนว่า “ยังไม่ยืนยัน”

### 4.2 สำรวจข้อความ

ค้นทั้งภาษาหลักและภาษาอังกฤษ เกมญี่ปุ่นอาจมีอังกฤษในเมนู หน้าเริ่มเกม ป้ายสถานที่ เอกสาร หรือเมนูทดสอบภายใน

เริ่มจากประโยคที่เห็นในภาพจริง แล้วลอง encoding ที่มีหลักฐานรองรับ เช่น ASCII หรือ Shift-JIS/CP932 สำหรับเกมญี่ปุ่น อย่าถือว่า PS1 ทุกเกมใช้ Shift-JIS; บางเกมใช้ตารางรหัสเฉพาะ ข้อความบีบอัด หรือประกอบข้อความขณะเล่น

ตรวจวิธีจบข้อความ ความยาว รหัสขึ้นบรรทัดใหม่ สี ความเร็ว หน้าต่าง การรอปุ่ม และตัวแปร เช่น `%d` หรือ `%s` สัญลักษณ์ที่ดูเหมือนข้อความธรรมดาอาจเป็นคำสั่งของ script

### 4.3 แยกชนิดของสิ่งที่เห็นบนจอ

| ชนิด | วิธีจัดการ |
|---|---|
| string ใน script/archive/EXE | ดึงเป็น CSV แล้ว encode กลับตามระบบเกม |
| string ที่ใช้ตารางรหัสเฉพาะ | สร้างตารางถอด/เข้ารหัสก่อนส่งออกและนำเข้า |
| ข้อความประกอบจากหลายส่วนหรือตัวแปร | เก็บรูปแบบและตรวจค่าตัวแปรในเกม |
| ภาพข้อความทั้งคำหรือทั้งบรรทัด | ดึงและแก้ texture |
| atlas ตัวอักษรที่เกมเรียงเป็นคำ | แก้ฟอนต์ พร้อมตรวจ mapping และระยะตัวอักษร |
| ข้อความในวิดีโอ | แยกเป็นงานวิดีโอภายหลัง |
| ยังไม่ทราบ | เก็บภาพ จุดในเกม และตรวจต่อ ไม่เดาชนิดจากหน้าตาอย่างเดียว |

การหา string ชื่อ `NEW GAME` เจอในไฟล์ไม่ได้ยืนยันว่าเป็นข้อความที่ใช้บนหน้าเมนูจริง ต้องตรวจการอ้างอิงหรือทดสอบเปลี่ยนตรงหน้าจอที่ต้องการ

**ผลลัพธ์ของขั้นนี้:** รายงานต้นฉบับ รายการไฟล์ ตาราง encoding ที่พิสูจน์แล้ว จุดข้อความตัวอย่าง และรายการที่ยังไม่ครอบคลุม

## 5. เลือกประโยคที่ผู้เล่นทดสอบได้ง่าย

ให้ผู้เล่นส่งภาพพร้อมข้อความต้นฉบับ ตำแหน่งฉาก วิธีเรียกข้อความ และข้อความก่อนหน้า/ถัดไป เลือกจุดต้นเกมหรือจุดที่ย้อนมาทดสอบซ้ำได้

ตัวอย่างลำดับที่เหมาะสม:

1. ชื่อไอเทมและคำถามว่าจะรับหรือไม่
2. ประโยคตรวจวัตถุหรือศพ พร้อมประโยคถัดไป
3. บทสนทนาหลายบรรทัดหรือหลายหน้า
4. เมนู เอกสาร และข้อความที่มีตัวเลข

อย่าสุ่มข้อความที่ผู้เล่นไม่รู้ว่าอยู่ตรงไหน การทดสอบที่มีจุดชัดเจนช่วยยืนยันได้ทั้งตำแหน่งไฟล์และผลของคำแปล

### 5.1 เปลี่ยนเป็นข้อความทดสอบด้วยภาษาเดิมก่อน

เปลี่ยนเพียงประโยคเดียวเป็นคำทดสอบสั้น ๆ ที่ฟอนต์เดิมรองรับ รักษาความยาวและโครงสร้างเดิมเท่าที่ทำได้ แล้วสร้าง BIN/CUE ใหม่

เมื่อผู้เล่นเห็นคำทดสอบ ต้องลองกดต่อ รับ/ไม่รับไอเทม หรือออกจากหน้าต่าง และเดินเข้าเหตุการณ์ถัดไปด้วย

**ผ่านเมื่อ:** เห็นคำที่เปลี่ยนในจุดที่ตั้งใจ และเล่นต่อได้ ถ้าไม่เปลี่ยน ตรวจไฟล์ที่เปิด save state, encoding, ตำแหน่ง และว่าจุดนั้นเป็นภาพหรือไม่ ก่อนเริ่มทำฟอนต์ไทย

## 6. ทดสอบภาษาไทยกับประโยคเดิม

### 6.1 เข้าใจข้อจำกัดของภาษาไทย

การแทนข้อความด้วย UTF-8 ไม่ทำให้เกมเก่าอ่านไทยได้เอง ต้องทำให้รหัสข้อความ การเลือก glyph และตัววาดของเกมเข้าใจตรงกัน

ตรวจพยัญชนะ สระบน/ล่าง วรรณยุกต์ สระหน้า `ำ` ช่องว่าง ตัวเลข เครื่องหมาย และการขึ้นบรรทัด ตรวจในขนาดที่แสดงจริง เพราะภาพฟอนต์ขยายใหญ่ที่ดูดีอาจอ่านไม่ออกเมื่อย่อกลับ

### 6.2 วิธีหลัก: ฟอนต์ส่วนประกอบที่ใช้ภาพซ้ำร่วมกัน

สำหรับเกมที่ต้องเพิ่มระบบฟอนต์ไทย ให้เริ่มจากวิธีส่วนประกอบตั้งแต่ต้น ไม่เริ่มด้วยการโหลดภาพสำเร็จของทุกกลุ่มอักษรไว้ใน RAM แล้วรอแก้เมื่อเกมค้าง สร้างภาพอ้างอิงที่อ่านง่ายไว้ตรวจนอกเกม จากนั้นเก็บส่วนภาพที่ซ้ำกันเพียงครั้งเดียว พร้อมตารางประกอบกลับ และใช้พื้นที่พักภาพขนาดคงที่สำหรับตัวอักษรที่กำลังแสดง

วิธีที่ใช้ได้ผลในงานนี้คือแบ่งภาพเป็นช่วงแถว เช่น ส่วนบน ตัวอักษร และส่วนล่าง แล้วประกอบกลับให้ตรงทุกพิกเซล ไม่ใช่แยกพยัญชนะ สระ และวรรณยุกต์ตาม Unicode อย่างเดียว จำนวนส่วนและตำแหน่งแบ่งต้องวัดจากฟอนต์ของเกมใหม่ ไม่คัดลอกค่าจากเกมเดิม

ก่อนใช้จริง ให้เปรียบเทียบขนาดรวมของภาพ ดัชนี สูตรประกอบ โค้ด และ cache กับทางเลือกอื่น ตรวจเวลาประกอบและขอบเขต RAM ตามหัวข้อ 6.5 หากเกมใช้ atlas เดิมที่แทนไทยได้โดยไม่เพิ่มพื้นที่ หรือข้อความเป็น texture ทั้งคำ ให้ใช้เส้นทางที่เหมาะสมด้านล่าง ไม่จำเป็นต้องเพิ่มตัวประกอบใหม่

**ทางเลือกสำรองตามโครงสร้างเกม:**

| วิธี | เหมาะกับกรณี | สิ่งที่ต้องตรวจ |
|---|---|---|
| แทน glyph เดิมด้วยไทย | มีช่องว่างหรือ glyph ที่ไม่ใช้ | ไม่ไปทับข้อความเดิมที่ยังจำเป็น |
| เพิ่มฟอนต์/ตารางรหัส | ระบบเดิมรองรับและวัดแล้วว่าพื้นที่เพียงพอ | ขนาดรวม การโหลด และขอบเขตรหัส |
| เก็บภาพกลุ่มอักษรสำเร็จแบบแรก | ใช้เป็นภาพอ้างอิงนอกเกม หรือมี glyph น้อยและพิสูจน์ว่างบ RAM พอ | ไม่โหลดภาพทั้งหมดไว้ถาวรโดยยังไม่วัดการใช้หน่วยความจำ |
| แก้ตัววาดหรือเพิ่ม runtime | ตัววาดเดิมไม่รองรับไทย | RAM, heap, buffer, overlay และเส้นทางเรียกใช้ |
| ทำเป็นภาพ | ข้อความบนเมนูคงที่หรือเป็น texture อยู่แล้ว | palette, UV, ขนาด และความโปร่งใส |

ไม่จำเป็นต้องใช้วิธีเดียวทั้งเกม เลือกทางที่ง่ายและเสี่ยงน้อยที่สุดที่ให้ผลถูกต้อง อย่าใช้ address หรือโค้ดฟอนต์จากอีกเกมโดยตรง

### 6.3 ลำดับทำฟอนต์และทดสอบประโยคแรก

1. ทำภาพอ้างอิงคำไทยสั้น ๆ ให้มีพยัญชนะ สระบน/ล่าง และวรรณยุกต์ ตรวจความอ่านง่ายที่ขนาดจริง
2. สร้างชุดส่วนประกอบและสูตรประกอบนอกเกม ถอดกลับแล้วเทียบทุกพิกเซลกับภาพอ้างอิง
3. วัดขนาดรวม กำหนดพื้นที่พักภาพคงที่ และตรวจพื้นที่โหลด/heap/overlay ก่อนเขียนตัวประกอบเข้าเกม
4. ตรวจตัวประกอบและ fallback อัตโนมัติ แล้วแทนชื่อไอเทมหรือประโยคเดิมเป็นไทย โดยรักษารหัสควบคุม สี และบรรทัด
5. ให้ผู้เล่นกดจบข้อความ เล่นต่อผ่านเหตุการณ์ และตรวจอย่างน้อยหนึ่งตัวอย่างของแต่ละระบบที่ต้องใช้ เช่น เมนูและเอกสาร
6. เมื่อได้คำแปล CSV ทั้งหมดกลับมา ให้สร้างชุดส่วนประกอบใหม่ ตรวจภาพครบชุดและวัด RAM ซ้ำก่อนนำเข้าจำนวนมาก ขนาดจากประโยคแรกไม่ใช่งบของทั้งเกม

บันทึกภาพและผลทดสอบของแต่ละรุ่น ไม่ใช้เพียงคำว่า “เห็นไทยแล้ว” เป็นหลักฐานว่าทุกระบบผ่าน

### 6.4 ตรวจระบบจอง RAM ทั้งเกมก่อน แล้วแยกสาเหตุเมื่อค้าง

**ให้ตรวจระบบจอง RAM ทั้งเกมจากไฟล์ก่อนขอให้ผู้เล่นไล่ทดสอบทีละฉาก** โดยทำตั้งแต่ต้นแบบภาษาไทย และทำซ้ำหลังนำเข้าคำแปลหรือเปลี่ยนฟอนต์/โค้ด วิธีนี้ช่วยพบปัญหาที่ฉากหลังอาจเรียกใช้ร่วมกันโดยไม่ต้องรอให้เล่นไปถึงทุกจุด:

1. แยกโปรแกรมหลักและไฟล์ฉาก/overlay ของทุกแผ่น ระบุฟังก์ชันจอง RAM และทำบัญชีทุกจุดที่เรียกใช้ รวมการเรียกผ่านตัวชี้ฟังก์ชันเท่าที่พิสูจน์ได้ ระบุไฟล์ ตำแหน่ง และขนาดคำขอที่เป็นค่าคงที่หรือคำนวณจากข้อมูล
2. ตรวจผลเมื่อจองไม่สำเร็จ โดยเฉพาะการใช้ pointer ศูนย์ไปเขียน/ล้างข้อมูล และตรวจช่วง RAM ที่โค้ดหรือฟอนต์ใหม่กันไว้กับ heap, ตัวโหลดฉาก และชุดล้าง RAM
3. สำหรับบัฟเฟอร์ที่มีสูตรสร้างจากข้อมูลเกม ให้คำนวณขนาดสูงสุดตามช่วงค่าที่รับจริง หากเปลี่ยนสูตรหรือความละเอียด ต้องค้นและแก้ทั้งตัวสร้างและตัวอ่านในโปรแกรมหลัก **และ** overlay ทุกไฟล์ แล้วสแกนซ้ำว่าไม่มีตัวอ่านแบบเดิมตกหล่น
4. สร้างรายงานแยก “พิสูจน์จากไฟล์/Save State ได้” กับ “จุดต้องสงสัยจากการสแกน” เปรียบเทียบคำขอกับก้อนว่างใหญ่สุดใน Save State หลายช่วง และออกชุดทดสอบที่แก้สาเหตุร่วมก่อนให้ผู้เล่นลองฉากตัวแทน

การสแกนไม่รู้ลำดับเหตุการณ์และสภาพ heap ทุกทางเลือก จึงยังต้องเล่นทดสอบฉากสำคัญและเส้นทางที่ได้รับผลกระทบ แต่ใช้ผลสแกนกำหนดว่าจะทดสอบตรงไหน แทนการรอพบเกมค้างทีละฉาก

ทำชุดเปรียบเทียบที่เปลี่ยนน้อยที่สุด: ต้นฉบับ, เปลี่ยนข้อความภาษาเดิม, เพิ่มฟอนต์แต่ไม่เปลี่ยนข้อความ, เปิด/ปิด hook, และลด/เพิ่มพื้นที่ RAM โดยคงส่วนอื่นเหมือนกัน

ตรวจว่าค้างก่อนเห็นข้อความ ขณะวาด หลังเลือกรับ หรือเมื่อโหลดฉาก ถ้าค้างหลังเริ่มเกมทั้งที่ยังไม่ถึงคำแปล อาจเป็นเรื่องการโหลดหรือหน่วยความจำ ต้องหาหลักฐาน ไม่สรุปว่าเป็นคำแปลยาวทันที

PS1 ที่เพิ่มโค้ดใน RAM ต้องตรวจทุกชุดที่ล้างหรือจัดสรรพื้นที่นั้น เช่น startup clear, heap หลายชุด และ scene overlay พื้นที่ที่ดูว่างในฉากหนึ่งอาจถูกเขียนทับในอีกฉาก

ก่อนเสนอให้แทนฟอนต์เดิม ต้องตรวจว่าฟอนต์นั้นอยู่ใน RAM ของเกมหรือเรียกจาก BIOS หากมาจาก BIOS จะไม่มีก้อน RAM ฟอนต์ญี่ปุ่นให้ยึดคืนตรง ๆ และพื้นที่ภาพโลโก้ที่เลิกแสดงแล้วอาจถูกนำไปใช้เป็น heap หรือข้อมูลฉากต่อไป ต้องเทียบไฟล์กับ RAM ของต้นฉบับด้วย ช่องที่เป็นศูนย์ในหลาย snapshot ยังไม่ใช่หลักฐานว่าปลอดภัยทุกฉาก

การผ่านต้นเกมยังไม่ยืนยันว่า RAM พอในฉากถัดไป เคยพบชุดฟอนต์ที่กัน 36 KiB เล่นต้นเกมได้ แต่ค้างเมื่อขึ้นบันได: snapshot แสดงว่าบัฟเฟอร์วาดภาพขนาด 24,800 bytes กลายเป็น pointer ศูนย์ และข้อมูลภาพไปทับส่วนระบบ ขณะที่ฟอนต์ยังอยู่ครบ เมื่อแพ็กข้อมูลฟอนต์เพิ่มโดยรักษาพิกเซลเดิมและลดพื้นที่ที่กันเหลือ 32 KiB ผู้ใช้ทดสอบผ่านจุดเดิมแล้ว วิธีตรวจที่ใช้ซ้ำได้คือเทียบ snapshot ต้นฉบับกับชุดแปล ตรวจขนาดก้อนว่างและบัฟเฟอร์ที่หายไป แล้วทดสอบแนวทางแก้ในจุดเดิม ตัวเลขนี้เป็นผลเฉพาะเกมที่ตรวจ ไม่ใช่งบ RAM มาตรฐานของ PS1 ทุกเกม

**บทเรียนจากงานจริง:** เคยพบว่าคำสั่งกระโดดยังอยู่ แต่โค้ดกับฟอนต์ปลายทางถูกล้างเป็นศูนย์ อีกช่วงหนึ่งชุดควบคุมที่จอง RAM 4 KiB ผ่าน แต่ 64 KiB ค้างแม้ยังใช้ภาษาต้นฉบับ ผลนี้ยืนยันตัวกระตุ้นในเกมที่ตรวจ แต่ไม่ได้พิสูจน์กลไกการจัดสรรทั้งหมด และไม่ได้แปลว่า 4 KiB เป็นค่าปลอดภัยของเกมอื่น

ตรวจทั้ง RAM ว่างรวมและก้อนว่างใหญ่สุดที่จัดสรรได้ ไม่ใช่ดูตัวเลขรวมอย่างเดียว อีกจุดหนึ่งพบ RAM ว่างรวม 2,144 bytes แต่ก้อนใหญ่สุด 1,808 bytes จึงจอง bitmap ข้อความ 1,920 bytes ไม่ได้ เกมเดิมนำ pointer ศูนย์ไปล้างข้อมูลต่อจนทับส่วนระบบ ต้องตรวจ pointer ของ object และเส้นทาง allocator/การล้างบัฟเฟอร์ประกอบด้วย หากลดข้อมูลฟอนต์ ให้พิสูจน์ว่าพิกเซลยังเหมือนเดิม เช่น ตัดเฉพาะแถวที่ว่างจริง แล้วทดสอบทั้งจุดใหม่และจุดที่เคยแก้ผ่านก่อนหน้านี้

ทดสอบคำถามและเหตุการณ์หลังตอบแยกกันด้วย: เคยแก้จนเปิดคำถามได้ แต่หลังตอบ “ใช่” เกมยังค้าง เพราะเหตุการณ์ถัดไปต้องจองตาราง 4,074 bytes ขณะที่ก้อนว่างใหญ่สุดมี 3,904 bytes แม้พื้นที่ว่างรวมมี 4,944 bytes ตาราง pointer ศูนย์เขียนทับระบบอีกครั้ง การเทียบข้อมูลที่ทับ RAM กับผลคำนวณของฟังก์ชันเดิมช่วยยืนยันต้นเหตุได้ การแพ็กฟอนต์ด้วย dictionary ของแถวภาพและรหัสสั้นช่วยคืนพื้นที่เพิ่มเติมโดยคงพิกเซลเดิม แต่ต้องทดสอบการจบเหตุการณ์จริงก่อนถือว่าแก้ผ่าน และห้ามใช้ save state หลังค้างเพราะ RAM ที่เสียแล้วถูกเก็บไว้ในเซฟด้วย

หากฉากถัดไปยังค้าง ให้ตรวจ object และบัฟเฟอร์ใหม่ อย่าถือว่าผ่านจุดตอบคำถามแล้วปลอดภัยทั้งฉาก ตัวอย่างจริงพบบัฟเฟอร์ภาพคู่ ตัวแรกจองได้แต่ตัวที่สองต้องใช้ 1,792 bytes ขณะที่ก้อนว่างใหญ่สุดเหลือ 1,456 bytes การคืน RAM เพิ่มเป็นเพียงชุดทดสอบจนกว่าจะเล่นผ่านเหตุการณ์จริง ตรวจความลื่นของฟอนต์ที่บีบอัดหนักขึ้นด้วย เพราะการลด RAM อาจแลกกับเวลา CPU

ก่อนให้ผู้เล่นไล่ทดสอบต่อ ให้สแกนโปรแกรมหลัก **และโค้ดในทุกไฟล์ฉาก/overlay** เพื่อทำบัญชีจุดเรียกตัวจัดสรร RAM ขนาดที่คำนวณได้ และจุดที่ใช้ pointer โดยไม่ตรวจว่าจองสำเร็จ แยกผลที่พิสูจน์ได้จากผลคัดกรองอัตโนมัติ หากเปลี่ยนรูปแบบตารางข้อมูล ให้ค้นตัวอ่านทั้งหมดทั้งใน EXE และ archive; การแก้เฉพาะโปรแกรมหลักอาจปล่อยตัวอ่านเก่าในฉากอื่นไว้

คำนวณเพดานของบัฟเฟอร์แต่ละชนิดจากสูตรและช่วงค่าที่เกมรับ เช่น ตารางภาพที่ใช้ช่วง 16 บิต แล้วเทียบกับก้อน RAM ว่างใหญ่สุดในหลาย Save State การลดขนาดบัฟเฟอร์ทั้งชนิดอาจแก้ได้หลายฉากพร้อมกัน แต่ต้องตรวจตัวสร้าง ตัวอ่าน ขอบเขต และผลภาพทุกเส้นทาง การสแกนไฟล์บอกจุดเสี่ยงและลดงานทดสอบได้ ยังไม่พิสูจน์ลำดับการจัดสรรหรือการแตกเป็นก้อนของ RAM ในทุกทางเลือกของผู้เล่น จึงต้องทดสอบช่วงสำคัญในเกมจริงต่อ

### 6.5 เกณฑ์ตรวจฟอนต์ส่วนประกอบก่อนนำเข้าเกม

แนวคิดแยกพยัญชนะ สระ และวรรณยุกต์จากงาน tile สามารถประยุกต์ข้ามเครื่องได้ แต่ตัวเลข VRAM และวิธีสลับ CHR ของ NES ไม่ใช่ข้อจำกัดของ PS1 ต้องตรวจตัววาดและหน่วยความจำของเครื่องเป้าหมายใหม่

ถ้าฟอนต์เดิมย่อความกว้างเป็นกลุ่มอักษร ภาพพยัญชนะเดี่ยวอาจไม่ตรงกับพยัญชนะในกลุ่มที่มีเครื่องหมาย การซ้อนภาพตรง ๆ จึงอาจผิด ต้องเลือกระหว่างจัดรูปฟอนต์ใหม่แล้วตรวจความอ่านง่าย หรือใช้ส่วนภาพที่ซ้ำกันโดยรักษาพิกเซลเดิม

ทำต้นแบบนอกเกม วัดภาพ ตำแหน่ง ดัชนี สูตรประกอบ โค้ด และ cache รวมกัน ทดลองถอดกลับทุก glyph/tile อัตโนมัติ แล้วเทียบภาพกับฐานที่ผู้ใช้ยอมรับ หากเขียนตัวประกอบด้วย MIPS ให้ตรวจ load delay, branch delay, register ที่ต้องรักษา, fallback ภาษาเดิม และขอบเขตการเขียน RAM ด้วย

ตัวอย่างการทดลองจริง: ข้อมูลภาพแบบแบ่งส่วนลด 1,881 bytes แต่ runtime รวมลด 1,744 bytes และหลังจัดแนวไฟล์โหลด คืน arena ได้เพียง 1,024 bytes อย่านำจำนวนไบต์ของภาพที่ลดลงไปกล่าวว่าเป็น RAM ที่คืนให้เกมทันที การตรวจภาพ 4,715 รูปแบบอัตโนมัติช่วยลดการตรวจทีละข้อความ แต่ไม่ได้จำลองการใช้ RAM ของทุกเหตุการณ์ในเกม

## 7. ดึงข้อความเป็น CSV ให้ผู้แปล

ทำเมื่อประโยคไทยตัวอย่างและระบบที่จำเป็นผ่านแล้ว ส่งออกข้อความจำนวนมากในครั้งเดียว เพื่อลดการทดสอบทีละประโยค

### 7.1 ไฟล์ที่ควรส่งให้ผู้แปล

- `text_original_language.csv` — ข้อความภาษาหลัก
- `text_english.csv` — ข้อความอังกฤษแยกต่างหากเมื่อมี
- `texture_text.csv` — คำบนภาพที่ต้องแก้เป็น texture
- `EXTRACTION_REPORT.md` — แหล่งที่ดึงได้ จำนวนรายการ และข้อจำกัด

หากเกมมีแต่ข้อความบนภาพ ให้ทำทะเบียนภาพและคำบนภาพแทนการอ้างว่าดึง string ได้ทั้งหมด

### 7.2 คอลัมน์ CSV ที่แนะนำ

| คอลัมน์ | ประโยชน์ |
|---|---|
| `id` | รหัสถาวรสำหรับจับคู่ตอนนำเข้า ไม่ใช้ลำดับแถวเป็นตัวตัดสิน |
| `category` / `group` | เมนู ไอเทม บทสนทนา เอกสาร หรือฉาก |
| `source_text` | ข้อความต้นฉบับที่ผู้แปลดูได้ |
| `thai_translation` | ช่องที่ผู้แปลแก้ |
| `previous_text` / `next_text` | บริบทต่อเนื่อง |
| `context` | จุดในเกม ผู้พูด หรือสถานการณ์ ถ้าทราบ |
| `source_type` | string, texture หรือประกอบขณะเล่น |
| `occurrence_count` | จำนวนตำแหน่งที่ข้อความนี้ปรากฏ |
| `original_bytes` / `capacity` | ข้อจำกัดที่พิสูจน์แล้ว พร้อมหน่วย |
| `controls` | ตัวแปรและคำสั่งที่ต้องรักษา |
| `status` / `notes` | รอแปล แปลแล้ว ตรวจแล้ว หรือรอตรวจในเกม |

ไฟล์สำหรับผู้แปลไม่จำเป็นต้องมีรายละเอียด binary ทุกคอลัมน์ แต่เครื่องมือต้องเก็บ manifest แยกที่เชื่อมกับ `id`: disc, file, archive entry, offset, encoding, raw bytes, ความยาว และทุก occurrence

เก็บ CSV เป็น UTF-8; ใช้ UTF-8 with BOM หากช่วยให้โปรแกรมตารางของผู้ใช้เปิดไทยถูกต้อง ต้อง quote ช่องที่มี comma, เครื่องหมายคำพูด หรือหลายบรรทัดให้ถูกต้อง

### 7.3 ข้อตกลงกับผู้แปล

แก้คำแปลและหมายเหตุได้ แต่ไม่เปลี่ยน `id` และต้นฉบับ ไม่ลบแถวและรหัสควบคุม ไม่เปลี่ยน `%d`, `%s` หรือสัญลักษณ์เฉพาะโดยไม่ตรวจระบบเกมก่อน

อธิบายให้ตรงกันว่า `\n` ในตารางเป็นข้อความ escape หรือแทนการขึ้นบรรทัดจริง แบบไหนต้องใช้กับเครื่องมือนำเข้า ความจุเป็นไบต์ กลุ่มอักษร glyph หรือพิกเซล ห้ามเรียกรวมว่า “จำนวนตัวอักษร” โดยไม่ระบุหน่วย

ข้อความเหมือนกันอาจแปลต่างกันตามบริบท หากรวมรายการซ้ำ ต้องยังเก็บตำแหน่งทั้งหมดไว้ และแยก ID เมื่อบริบทต่างจนคำแปลเดียวใช้ไม่ได้

### 7.4 อย่าอ้างว่าครบทั้งเกมโดยไม่มีหลักฐาน

รายงานให้ชัดว่า “ดึงข้อความที่ตรวจพบจากไฟล์ใด” และ “ยังไม่รวมอะไร” เช่น ภาพ วิดีโอ encoding ที่ยังไม่รู้ หรือข้อความประกอบขณะเล่น

กรองชื่อไฟล์ log ของผู้พัฒนา ข้อความ SDK และ byte ที่บังเอิญดูเป็นภาษาอังกฤษออกจากคำที่ใช้จริง แต่อย่าทิ้งรายการที่ยังสงสัยโดยไม่เก็บบันทึก

ตรวจทั้งสองแผ่น อย่าคัดลอกคำแปลแผ่นแรกลงอีกแผ่นเพียงเพราะชื่อเกมเหมือนกัน หากไฟล์ร่วมกันจริง ให้ยืนยันจากเนื้อหาหรือค่าแฮชก่อน

หลังดึงข้อความรอบแรก ให้สแกนซ้ำแบบกว้างกว่าเกณฑ์คัดกรองเดิม โดยเฉพาะประโยคสั้นหรือมีคันจิมากซึ่งอาจถูกตัวกรองสัดส่วนฮิรางานะ/คาตากานะตัดทิ้ง เก็บรายการที่น่าสงสัยแยกไว้เพื่อตรวจบริบท อย่าอ้างว่า CSV ครบจากจำนวนรายการเพียงอย่างเดียว

## 8. ตรวจและเกลาคำแปลก่อนนำเข้า

### 8.1 ตรวจภาษา

ตรวจความหมายกับต้นฉบับและประโยคข้างเคียง ชื่อคน สถานที่ ไอเทม สรรพนาม และศัพท์เฉพาะให้สม่ำเสมอ แยกภาษาพูด บันทึก และคำสั่งเมนูตามบริบท

ทำอภิธานศัพท์กลาง อย่าแปลอังกฤษเป็นไทยโดยอัตโนมัติถ้าเป็นชื่อเฉพาะ สัญลักษณ์ปุ่ม หรือชื่อที่ผู้เล่นต้องใช้เทียบกับ UI

### 8.2 ตรวจทางเทคนิค

- ID ครบ ไม่ซ้ำ ไม่สูญหาย และจับคู่ manifest ได้
- แยกช่องคำแปลว่างว่า “ยังไม่แปล” หรือ “ตั้งใจคงต้นฉบับ”
- รหัสควบคุมและ placeholder ครบตามที่ระบบต้องการ
- ไม่เกิด terminator หรือคำสั่งที่ parser จะเข้าใจผิดภายในข้อความ
- ตัวอักษรทั้งหมดมี glyph ที่ใช้แสดงได้
- ขนาดหลัง encode และความกว้างบนจออยู่ในขอบเขต
- จำนวนบรรทัดและความสัมพันธ์กับประโยคถัดไปยังถูกต้อง

หากคำแปลยาวเกิน ให้ปรับประโยคก่อนบีบฟอนต์จนอ่านยาก การขยายพื้นที่ข้อความหรือย้ายข้อมูลต้องทำเมื่อเข้าใจ pointer และตัวอ่านแล้ว

เก็บคำแปลที่ผู้ใช้ส่งไว้ และทำไฟล์ฉบับตรวจแยก เช่น `text_reviewed.csv` พร้อม `translation_changes.csv` ซึ่งมี ID, ก่อนแก้, หลังแก้ และเหตุผล การย้ายคำไปอีกบรรทัดทำได้เฉพาะเมื่อยืนยันว่าอยู่ในลำดับเดียวกันจริง

## 9. นำคำแปลเข้าเกมอย่างควบคุมได้

### 9.1 สร้างแผนก่อนเขียนไฟล์

แผนนำเข้าต้องระบุว่าแต่ละ ID แทนที่ตำแหน่งใด ใช้รหัสและ glyph ใด รักษาคำสั่งส่วนไหน และรายการใดเว้นไว้พร้อมเหตุผล

ก่อนเขียนทุกตำแหน่ง ให้เทียบ raw bytes กับต้นทางที่คาดไว้ ถ้าไม่ตรง ให้หยุดตรวจรุ่นหรือพาธ อย่าเขียนทับด้วย offset ที่เดาไว้

หลังนำเข้า ให้สแกนไฟล์ฉากและโปรแกรมอีกครั้งเพื่อหาข้อความภาษาเดิมที่ยังไม่เปลี่ยน แยกผลจากข้อมูลภาพหรือไบต์ที่บังเอิญถอดเป็นตัวหนังสือ แล้วเทียบกับภาพในเกม ข้อความญี่ปุ่นบรรทัดหนึ่งพร้อมไทยอีกบรรทัดหนึ่งอาจเป็นสอง string คนละตำแหน่งที่เกมแสดงต่อกัน ไม่จำเป็นต้องเป็นวิดีโอหรือภาพ

### 9.2 เลือกการจัดพื้นที่ตามโครงสร้างเกม

- **แทนที่ในช่องเดิม:** เหมาะกับการเริ่มทดลอง รักษาขนาดและ pointer; padding ต้องใช้รูปแบบที่เกมอ่านได้
- **ย้ายข้อความไปพื้นที่ใหม่:** ต้องแก้ pointer, ความยาว, alignment และวิธีโหลดให้ครบ
- **ขยาย archive หรือไฟล์:** ต้องปรับตารางภายใน ขนาด และระบบอ้างอิงทั้งหมดที่เกี่ยวข้อง

ไม่ควรเปลี่ยนความยาว string แล้วปล่อยให้ข้อมูลถัดไปเลื่อนโดยไม่อัปเดตโครงสร้าง

### 9.3 ทดสอบเป็นชุดก่อนรวมทั้งหมด

ก่อนส่งรุ่นรวมให้เล่น สแกนระบบจอง RAM ของโปรแกรมหลักและไฟล์ฉากทุกแผ่นตามหัวข้อ 6.4 อีกครั้ง บันทึกจุดที่ตรวจได้ ขนาดบัฟเฟอร์เสี่ยง และตัวอ่านที่ยังใช้รูปแบบเก่า แล้วเลือกฉากทดสอบจากผลตรวจ การเล่นไล่ฉากอย่างเดียวไม่ใช่วิธีหลักในการค้นข้อผิดพลาดด้าน RAM

เริ่มจากหมวดที่รู้จุดทดสอบ เช่น ไอเทมและข้อความตรวจวัตถุ แล้วค่อยเมนู เอกสาร บทสนทนา และทั้งเกม ทำรุ่นย่อยที่ย้อนกลับได้ หากมีปัญหาให้แบ่งชุดย่อยเพื่อหาว่าหมวดหรือตัววาดใดเกี่ยวข้อง

หลังรวมคำแปล อย่าข้ามฉากต้นเกมที่เคยผ่านตอนมีเพียงประโยคเดียว เพราะฟอนต์ใหญ่ขึ้นหรือข้อมูลเพิ่มอาจเปลี่ยนการใช้หน่วยความจำ

ใช้ฟอนต์ส่วนประกอบตามหัวข้อ 6 เป็นฐานของการนำเข้าทุกชุด สร้างและตรวจภาพที่ใช้ทั้งหมดอัตโนมัติแทนการให้ผู้เล่นเปิดดูทีละประโยค การทดสอบด้วยมือเน้นความอ่านง่าย บริบท ตัวแปร และการจบเหตุการณ์/เปลี่ยนฉาก หากพื้นที่เกินงบให้ทบทวนการจัดเก็บก่อนสร้างรุ่นเล่น ไม่เพิ่มพื้นที่ที่กันจาก heap โดยอาศัยเพียงว่าต้นเกมยังผ่าน

## 10. ถ้าข้อความเป็น texture ให้แก้ภาพ

### 10.1 ดึงภาพพร้อมข้อมูลที่ต้องรักษา

เก็บภาพต้นฉบับตำแหน่งจริง รวม palette/CLUT, bit depth, ขนาด, ความโปร่งใส, ข้อมูล texture page/UV และโครงสร้าง container ที่ทราบ PS1 อาจใช้ TIM หรือภาพเฉพาะของเกม อย่าแก้เฉพาะ PNG แล้วถือว่านำกลับได้ทันที

ทำภาพ preview หรือแผ่นรวมภาพเพื่อสำรวจคำบนเมนู ทั้งสถานะปกติ เลือกอยู่ กดไม่ได้ และหน้าจอภาษาอื่นที่แชร์ภาพเดียวกัน

### 10.2 แก้คำและนำกลับ

ใช้คำไทยกระชับให้พอดีกับพื้นที่วาด รักษา palette และสีโปร่งใส ตรวจตัวอักษรในความละเอียดจริง และระวังพื้นที่ติดกันใน atlas

เข้ารหัสภาพกลับในรูปแบบที่เกมอ่านได้ ถ้าคงขนาดและ layout เดิมได้จะตรวจง่ายกว่า การเปลี่ยนขนาดต้องตรวจ UV, การโหลด และพิกัดวาดร่วมด้วย

ทดสอบทั้งการแสดงและการเลือกเมนู หากทั้งหมดเป็นภาพ ให้แปลผ่านทะเบียน texture; หากมีทั้ง string และภาพ ให้ทำสองระบบควบคู่กัน

**บทเรียนจากงานจริง:** คำบนเมนูบางคำมีทั้ง string ใน EXE และภาพบนหน้าเริ่มเกม การแปล string ทำสำเร็จ แต่หน้าจอยังเป็นอังกฤษเพราะใช้ภาพอีกชุด ต้องพิสูจน์หน้าจอที่ใช้งานจริง

## 11. ข้อความที่ใช้ตัววาดพิเศษ

หน้าจอหลักอาจรองรับไทยแล้ว แต่ป้ายสถานที่ เอฟเฟกต์ตัวอักษร หรือเครดิตอาจยังใช้ตัววาด ASCII แยกต่างหาก อาการอาจเป็นตัวหาย เหลือบางตัว หรือระยะผิด

หากเจอปัญหา ให้เทียบภาพต้นฉบับและภาพแปล ตรวจเส้นทางวาดรหัสของหน้าจอนั้น แล้วเลือกเพิ่มการรองรับเฉพาะส่วน ทำข้อความเป็นภาพ หรือคงต้นฉบับไว้ชั่วคราวตามขอบเขตที่ตกลง

รายการที่คงภาษาเดิมต้องอยู่ในรายงานและคู่มือแพตช์ ไม่ระบุว่าแปลครบแล้ว การแสดงฟอนต์หนึ่งหน้าต่างถูกต้องไม่ได้ยืนยันทุกหน้าจอ

## 12. วิดีโอและซับไทย — ทำภายหลังได้

วางเป็นงานเสริมหลังระบบข้อความนิ่ง ไม่จำเป็นต้องทำก่อนสร้างแพตช์ข้อความ

เมื่อเริ่มงาน ให้ทำทะเบียนคลิป ดึงไฟล์ดั้งเดิมและแปลงสำเนาเป็นรูปแบบที่ตัดต่อสะดวก ส่งให้ผู้ใช้ฝังซับก่อน จากนั้นทดลองนำกลับเพียงคลิปเดียวให้ผ่านทั้งภาพ เสียง ตอนจบ และฉากถัดไป แล้วค่อยทำทั้งแผ่น

MP4 ที่แก้แล้วไม่ใช่ไฟล์ที่ PS1 เล่นได้โดยตรง ต้องแปลงกลับเป็นชนิด stream ที่เกมใช้งาน และตรวจความละเอียด อัตราเฟรม เสียง ระยะเวลา ขนาด sector, interleave และจุดจบตามต้นฉบับของคลิปนั้น

อย่าคัดลอกค่า fps หรือเสียงจากเกมอื่น แม้ชื่อชนิดไฟล์เหมือนกัน คลิปที่ไม่มีบทพูดหรือไม่ต้องแก้ให้คงไว้และบันทึกในรายการ

ถ้าขนาดเพิ่มเกินพื้นที่เดิม ต้องวิเคราะห์ระบบโหลดก่อนขยาย อาการท้ายคลิปขาด เสียงหาย หรือฉากถัดไปไม่โหลดต้องทดสอบในเกม เพราะการเปิดวิดีโอที่แปลงออกมาดูบนคอมพิวเตอร์อย่างเดียวไม่เพียงพอ

## 13. สร้างแผ่นและตรวจความถูกต้องของไฟล์

แยก file offset, archive offset, LBA และ physical sector offset ให้ชัด ไม่ใช้แทนกัน เกมอาจอ้างไฟล์ผ่านระบบไฟล์หรือผ่านตำแหน่งที่ฝังในโปรแกรม

สำหรับ PS1 ต้องตรวจรูปแบบ sector ตาม track ที่แก้ ข้อมูลผู้ใช้และ header ไม่เท่ากันทุกชนิด คำนวณ EDC/ECC เฉพาะส่วนที่ต้องมีตามชนิด sector; อย่าเขียนแบบ ISO 2048 bytes ลง raw BIN โดยไม่เข้าใจ layout

หลังสร้าง ให้ตรวจอย่างน้อย:

- ต้นฉบับยังมีค่าแฮชเดิม
- อ่านไฟล์ที่แก้กลับจาก BIN ได้ตรงกับข้อมูลที่ตั้งใจนำเข้า
- ขนาด ตาราง archive, pointer และ alignment ถูกต้อง
- ไฟล์/sector ที่ไม่ได้ตั้งใจแก้ยังตรงกับฐานที่ใช้
- ส่วนที่เพิ่มมีตำแหน่งโหลดและขอบเขตหน่วยความจำที่ตรวจแล้ว
- CUE อ้างอิงชื่อ BIN และโครงสร้าง track จริง

ตัวอย่าง CUE แบบนี้ใช้ได้เฉพาะแผ่นที่ยืนยันว่าเป็น BIN เดียวและ track เดียวชนิดดังกล่าว:

```cue
FILE "test.bin" BINARY
  TRACK 01 MODE2/2352
    INDEX 01 00:00:00
```

แผ่นที่มีหลาย track หรือ audio track ต้องรักษารายการ track และ index ตามจริง ไม่สร้าง CUE แบบง่ายทับข้อมูลเดิม

## 14. แผนทดสอบก่อนออกแพตช์

### 14.1 ระบุไฟล์และวิธีเริ่มเกม

ส่งพาธ CUE และชื่อรุ่นที่ชัดเจน หากแก้ EXE, ฟอนต์ หรือระบบโหลด ให้เริ่มเกมใหม่เป็นการตรวจหลัก อย่าใช้ Resume/save state ของรุ่นก่อนแทนการบูตใหม่ เพราะอาจมีโค้ดและข้อมูลเก่าค้างอยู่ใน RAM

เซฟเมมโมรีการ์ดใช้ทดสอบช่วงหลังได้ แต่ต้องตรวจด้วยว่าเกมโหลดใหม่และข้อมูลเซฟสัมพันธ์กับการแก้ไขอย่างไร ตรวจการสร้างเซฟ โหลดเซฟ และเปลี่ยนแผ่นตามการใช้งานจริง

### 14.2 รายการทดสอบ

- [ ] สแกนจุดจอง RAM และตัวอ่านบัฟเฟอร์ที่เปลี่ยนในโปรแกรมหลักกับไฟล์ฉากทุกแผ่น; บันทึกข้อจำกัดของการสแกน
- [ ] เปิดเกมและเข้าเมนูหลักได้
- [ ] เริ่มเกมใหม่และผ่านช่วงโหลดแรก
- [ ] ประโยคตัวอย่างไทยอ่านได้และกดต่อได้
- [ ] รับ/ไม่รับไอเทมแล้วเล่นต่อได้
- [ ] ตรวจวัตถุ บทสนทนา และข้อความหลายหน้า
- [ ] เมนูทุกสถานะ เอกสาร ชื่อไอเทม ตัวเลข และตัวแปร
- [ ] ประโยคยาวไม่ล้นจอ สระ/วรรณยุกต์ไม่หาย
- [ ] texture แสดงถูก และเมนูเลือกใช้งานได้
- [ ] โหลดฉากต่อไปได้ทุกจุดสำคัญที่แก้
- [ ] เซฟและโหลดจากเมมโมรีการ์ดได้
- [ ] แต่ละแผ่นและการเปลี่ยนแผ่นผ่าน
- [ ] ถ้าแก้วิดีโอ: ภาพ เสียง ซับ และการจบคลิปผ่าน
- [ ] ทดสอบเส้นทางอื่นหรือเงื่อนไขทางเลือกที่เกี่ยวข้อง

ไม่จำเป็นต้องเล่นจากศูนย์ซ้ำทุกครั้งที่แก้เล็กน้อย แต่ต้องทดสอบส่วนที่ได้รับผลกระทบ และรุ่นรวมสุดท้ายต้องมีผลเล่นจริงตามขอบเขตที่จะประกาศ

### 14.3 แบบบันทึกผล

```csv
build,disc,test_point,start_method,result,screenshot,notes
v01,1,รับไอเทมต้นเกม,new_game,PASS,ภาพตัวอย่าง,เห็นไทยและเข้าฉากต่อได้
v02,1,หน้าเอกสาร,memory_card,FAIL,ภาพตัวอย่าง,บรรทัดสุดท้ายล้นจอ
```

ใช้สถานะ `ยังไม่ทดสอบ`, `ผ่าน`, `ไม่ผ่าน`, `ไม่อยู่ในขอบเขต` แยกกันชัด ผลตรวจ binary ไม่ใช้แทนผลเล่นในเกม

หากยังทดสอบไม่ครบ สามารถออกชุดทดลองโดยระบุส่วนที่ผ่านและส่วนที่รอได้ ใช้คำว่า RC หรือรุ่นทดลองอย่างตรงไปตรงมา แต่การเรียกรุ่นสมบูรณ์ควรมีหลักฐานตามรายการทดสอบที่ตกลงไว้

## 15. สร้างแพตช์สำหรับผู้เล่น

### 15.1 เลือกรุ่นต้นทางและปลายทาง

แพตช์เผยแพร่ควรสร้างจากต้นฉบับที่ระบุไว้ไปยัง BIN รุ่นสุดท้ายโดยตรง เพื่อให้ผู้เล่นไม่ต้องลงแพตช์ทดลองเรียงหลายรุ่น

แยกแพตช์แต่ละแผ่น ระบุภูมิภาค revision, ขนาดต้นฉบับ, CRC32/SHA-256 และ SHA-256 ผลลัพธ์ให้ครบ เลือกรูปแบบ BPS หรือ xdelta ตามขนาดและเครื่องมือที่ใช้งานได้จริง

อย่าถือว่าตัวอ่าน BPS ทุกตัวรองรับไฟล์ใหญ่หรือทุกคำสั่ง ตรวจรูปแบบคำสั่งที่ตัวสร้างใช้และความสามารถของตัวอ่านโดยตรง ตัวอ่านเว็บจากงานก่อนรองรับชุดคำสั่งที่แพตช์ของงานนั้นใช้ ไม่ใช่ตัวอ่าน BPS ทั่วไปทุกชนิด

### 15.2 ตรวจลงแพตช์กลับ

1. สร้างแพตช์จากต้นฉบับไปยังไฟล์ที่ทดสอบ
2. ใช้ตัวอ่านแพตช์อีกขั้นตอนลงบนต้นฉบับใหม่
3. เทียบผลลัพธ์ byte-for-byte หรือ SHA-256 กับ BIN ปลายทาง
4. ตรวจ CUE และนำผลลัพธ์ไปทดสอบเปิดเกม

การตรวจนี้พิสูจน์ว่าแพตช์ถ่ายทอดไฟล์ถูกต้อง ไม่ได้พิสูจน์ว่าไม่มีบั๊กในตัวเกม

ชุดเผยแพร่ควรมีแพตช์ คู่มือผู้เล่น manifest ค่าแฮช รายการส่วนที่แปล/คงภาษาเดิม และประวัติรุ่น ไม่แนบ BIN ต้นฉบับหรือ BIN ที่แพตช์แล้วในชุดเว็บ

## 16. ทำเว็บลงแพตช์เหมือนงานที่ผ่านมา

### 16.1 ขั้นตอนที่ผู้เล่นเห็น

```text
เลือกแผ่น → เลือก BIN ต้นฉบับ → ตั้งชื่อ BIN ใหม่
→ ตรวจไฟล์ → ดาวน์โหลดแพตช์และเขียนผลลัพธ์
→ ตรวจผล → ดาวน์โหลด CUE → เปิด CUE ในโปรแกรมเล่นเกม
```

ไฟล์ต้นฉบับอ่านภายในเครื่องผู้เล่น เว็บดาวน์โหลดเฉพาะแพตช์ อย่าสร้างระบบอัปโหลด BIN โดยไม่จำเป็น

ถ้าผู้เล่นบันทึกเป็น `test.bin` ให้สร้าง `test.cue` และภายในเขียน `FILE "test.bin" BINARY` ใช้ชื่อจริงจากผลการบันทึกสำเร็จ ไม่ใช้ชื่อแนะนำเริ่มต้น และแยกข้อมูล track ตามแผ่นจริง

### 16.2 รับมือไฟล์ใหญ่

เลือกการอ่านและเขียนเป็นช่วง ๆ ไม่โหลดต้นฉบับ แพตช์ และ BIN ผลลัพธ์ทั้งหมดเข้า RAM พร้อมกัน ประมวลผลไฟล์ต้นฉบับเพื่อตรวจ CRC ก่อนดาวน์โหลดข้อมูลจำนวนมาก

รองรับไฟล์ BPS ในเครื่องเป็นทางเลือกได้ แต่ผู้เล่นทั่วไปควรเลือก BIN และกดเริ่มได้โดยไม่ต้องเลือกแพตช์เอง

หากต้องแบ่งแพตช์เป็นหลายส่วน ให้กำหนดลำดับและขนาดที่ตรวจได้ รวมสตรีมตามลำดับเดิม แล้วตรวจ checksum และผลลัพธ์ท้ายงาน ห้ามเปลี่ยนเนื้อหา binary ระหว่างแบ่งหรืออัปโหลด

`Content-Length` อาจเป็นขนาดข้อมูลที่บีบอัดก่อนเบราว์เซอร์ถอดออก ไม่ควรเทียบกับจำนวนไบต์หลังถอด gzip อย่างตรง ๆ ให้ตรวจจำนวนไบต์ที่อ่านได้กับ manifest และตรวจ checksum ของแพตช์/ผลลัพธ์

### 16.3 โฮสต์และการเผยแพร่

ใช้โฮสต์ที่ผู้ใช้เลือก ตรวจข้อจำกัดไฟล์เดี่ยว ขนาดเว็บ แบนด์วิดท์ และการรองรับ stream ก่อนอัปโหลด หากเก็บแพตช์คนละโดเมน ต้องตั้ง CORS ให้เว็บอ่านได้

GitHub Pages ใช้หน้าเว็บ static ได้ งานที่ผ่านมาทดลองแบ่งแพตช์เป็นส่วนละ 64 MiB แล้วดึงจากโดเมนเดียวกัน แต่ขนาดเว็บไซต์และประวัติ repository จะโตตามไฟล์ binary จึงไม่ควรถือว่าวิธีนี้เหมาะกับทุกเกมหรือทุกจำนวนผู้เล่น ตรวจข้อจำกัดบริการ ณ วันเผยแพร่ และใช้ object storage เมื่อเหมาะสมกว่า

ก่อนเผยแพร่ ทำหน้าเว็บที่ตรวจได้ให้เสร็จ ระบุ URL ปลายทางและผลกระทบต่อเว็บเดิม ใช้หน้าทดลอง เช่น `games/test.html` หากต้องการ ถ้าผู้ใช้อนุญาตการเผยแพร่ไว้แล้ว ให้ทำต่อในขอบเขตนั้น ไม่ถามยืนยันซ้ำโดยไม่จำเป็น

### 16.4 ตรวจหลังขึ้นเว็บ

- หน้าเว็บและไฟล์ตั้งค่าเป็นรุ่นล่าสุด
- แพตช์ทุกส่วนดาวน์โหลดได้และ checksum ถูก
- สตรีมจาก URL จริงสร้าง BIN ได้ตรง SHA-256 รุ่นที่ทดสอบ
- ไฟล์ต้นฉบับผิดแผ่นหรือผิดรุ่นถูกปฏิเสธอย่างเข้าใจง่าย
- การดาวน์โหลดที่ขาดหรือผิดพลาดไม่ถูกแจ้งว่าทำสำเร็จ
- ชื่อ CUE และ BIN ตรงกัน รวมชื่อที่ผู้เล่นตั้งเอง
- ไม่มี BIN เกมถูกส่งขึ้นเว็บหรือหลุดไปอยู่ในชุดเว็บไซต์
- มีข้อความแนะนำ browser และสถานะการทดสอบที่ตรงกับความจริง

การทดสอบในเครื่องผ่านยังไม่พอ ต้องทดสอบ URL จริง เพราะ cache, gzip, CORS และการเผยแพร่ของโฮสต์อาจทำให้พฤติกรรมต่างกัน

### 16.5 มือถือ

แยก “เปิดหน้าเว็บได้” กับ “แพตช์และบันทึกไฟล์ใหญ่ได้” ตรวจ API ที่เครื่องนั้นมีจริง พร้อมทดสอบ BIN และ CUE บนเครื่องจริงก่อนประกาศรองรับ

เว็บงานก่อนใช้ `showSaveFilePicker` จึงใช้ได้เฉพาะเบราว์เซอร์ที่รองรับวิธีนี้ การรองรับเปลี่ยนได้ตามรุ่น browser ห้ามใช้คำว่า “มือถือได้ทั้งหมด” จากการทดสอบคอมพิวเตอร์ ถ้าต้องทำทางเลือกสำหรับ browser อื่น ให้วิเคราะห์พื้นที่ชั่วคราวและวิธีดาวน์โหลดไฟล์ใหญ่แยกต่างหาก

## 17. ตารางอาการและสิ่งที่ควรตรวจ

| อาการ | เริ่มตรวจจาก |
|---|---|
| ข้อความไม่เปลี่ยน | รุ่น CUE, save state, offset, สำเนาข้อความ และ string/texture |

ใช้ตารางนี้เพื่อเลือกสิ่งที่จะตรวจ ไม่ใช่ฟันธงสาเหตุโดยไม่มีหลักฐาน

สแกนระบบจอง RAM ของโปรแกรมหลักและไฟล์ฉากทุกแผ่นก่อนให้ฉันเล่นไล่ฉาก ตรวจขนาดคำขอ การใช้ pointer เมื่อจองไม่สำเร็จ และตัวสร้าง/ตัวอ่านบัฟเฟอร์ที่แก้ แล้วส่งรายงานจุดเสี่ยงพร้อมฉากที่ควรทดสอบ

## 20. เกณฑ์จบงานและสิ่งที่นำจากงานเก่าไปใช้ได้

งานจบเมื่อคำแปลที่อยู่ในขอบเขตผ่านการตรวจและการเล่นจริง แพตช์ลงบนต้นฉบับได้ตรงรุ่นที่ทดสอบ เว็บดาวน์โหลด/สร้างไฟล์ได้ และผู้เล่นมี CUE กับคู่มือเปิดเกมที่ถูกต้อง หากยังมีรายการรอ ต้องระบุว่าเป็นรุ่นทดลองและบันทึกงานค้างไว้

นำแนวทาง โครงสร้าง CSV ระบบบันทึกค่าแฮช แผนทดสอบ และ UI เว็บไปใช้ซ้ำได้ แต่ parser archive, encoding, control codes, glyph mapping, RAM address, hook, track layout และตัวโหลดวิดีโอต้องตรวจใหม่สำหรับแต่ละเกม

ในโฟลเดอร์งานเดิม มีตัวอย่างเครื่องมือให้ศึกษา ได้แก่ `explore.py`, `extract_translation_index.py`, `extract_english_index.py`, `prepare_translation_import.py`, `prepare_menu_textures.py`, `build_release_patches.py` และชุด `web_patcher/` เครื่องมือเหล่านี้ผูกกับโครงสร้างเกมเดิม จึงเป็นตัวอย่างการออกแบบ ไม่ใช่คำสั่งสำเร็จรูปสำหรับเกมใหม่

หลักฐานที่ใช้เรียบเรียงบทเรียนในคู่มือนี้มาจากรายงานการล้างฟอนต์ใน RAM, ชุดควบคุม RAM 4/64 KiB, การแก้ฟอนต์แบบ compact, การตรวจเมนูที่เป็น TIM, การคืนป้ายที่ใช้ตัววาด ASCII, ผลทดลองข้อความและวิดีโอของผู้เล่น และการเทียบ SHA-256 จากแพตช์บนเว็บจริง
